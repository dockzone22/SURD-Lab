### 0.1 인수인계 목적

본 문서는 SURD Lab 홈페이지의 기본 운영 방법과 콘텐츠 수정 절차를 안내하기 위해 작성하였다.

피인계자는 특별한 사유가 없는 한 홈페이지의 기본 구조와 디자인을 변경하지 않고, 기존 틀 안에서 연구실 정보를 추가·수정·삭제하는 것을 원칙으로 한다. 특히 다음 요소는 임의로 변경하지 않는다.

* 전체 페이지 구성 및 메뉴 순서
* 헤더와 푸터
* 홈페이지의 색상, 글꼴 및 디자인 체계
* PC·모바일 반응형 구조
* 각 페이지의 기본 레이아웃
* 데이터가 화면에 표시되는 방식
* GitHub Pages 배포 설정 및 도메인 설정

홈페이지 구조를 변경하면 특정 페이지뿐 아니라 모바일 화면, 메뉴, 데이터 연결 및 배포 과정에서 예상하지 못한 문제가 발생할 수 있다. 따라서 일상적인 관리에서는 기존 내용을 추가·삭제·수정하는 수준으로 작업한다.

구조나 디자인 변경이 반드시 필요한 경우에는 원본을 즉시 수정하지 말고, 별도 브랜치 또는 복사본에서 충분히 시험한 뒤 반영한다.

### 0.2 홈페이지 제작 환경

SURD Lab 홈페이지는 정적 웹사이트 형태로 제작되었으며, 주요 구성 파일은 HTML, CSS, JavaScript 및 데이터 파일이다. 홈페이지 제작과 수정 과정에서는 다음 도구를 활용하였다.

* ChatGPT: 홈페이지 구성 검토, 코드 작성·수정, 오류 분석 및 관리 방법 정리
* Google Antigravity: 저장소 파일 확인, 코드 수정, 로컬 테스트 및 GitHub 반영
* GitHub: 홈페이지 파일 저장, 변경 이력 관리 및 배포
* GitHub Pages: GitHub 저장소의 파일을 실제 홈페이지로 공개

Antigravity는 무료이므로 다운로드 받고, git bash 다운로드도 권장한다.
Github은 반드시 회원가입하여야 한다.
.js 파일(javascript)를 수정하기 위해 visual code studio 다운로드를 하면 좋다
or, 연구실 컴퓨터라면 시작버튼>code를 검색하면 나올 수도 있다.
ChatGPT나 Antigravity가 제안한 코드를 그대로 반영하기보다는 각 ai들에게 서로 cross-check하도록 하는 것을 권장한다.
작업 전에는 프롬프트에 수정 대상과 변경 범위를 명확히 전달하고, 작업 후에는 수정된 파일과 실제 화면을 반드시 확인해야 한다.

AI 도구를 사용할 때는 다음 원칙을 지킨다.

1. 먼저 저장소 전체 구조와 기존 코드를 확인하도록 지시한다.
2. 홈페이지의 기존 디자인과 구조를 유지하도록 명시한다.
3. 수정할 페이지와 항목을 구체적으로 지정한다.
4. 관련 없는 파일은 수정하지 않도록 지시한다.
5. 작업 후 수정된 파일 목록과 수정 내용을 보고받는다.
6. PC와 모바일 화면에서 모두 확인한다.
7. 이상이 없을 때만 GitHub에 commit 및 push한다.
8. 계정 비밀번호, 인증번호, 개인 연락처 등 민감한 정보는 AI 대화창에 입력하지 않는다.

### 0.3 GitHub의 역할

GitHub는 홈페이지를 구성하는 파일을 보관하고 변경 이력을 기록하는 서비스이다. SURD Lab 홈페이지는 GitHub 저장소에 저장되어 있으며, 저장소의 `main` 브랜치에 반영된 내용을 바탕으로 GitHub Pages가 홈페이지를 공개한다.

기본적인 반영 과정은 다음과 같다.

1. 저장소를 컴퓨터로 불러온다(pull).
2. 필요한 콘텐츠를 수정한다.
3. 로컬 환경에서 수정 결과를 확인한다.
4. 변경된 파일을 확인한다.
5. 변경 내용을 기록한다(commit).
6. GitHub에 업로드한다(push).
7. GitHub Pages의 배포가 완료될 때까지 기다린다.
8. 실제 홈페이지에서 수정 결과를 확인한다.

GitHub에서 사용하는 주요 용어는 다음과 같다.

* Repository: 홈페이지 파일과 변경 이력이 보관되는 저장소
* Branch: 작업 흐름을 구분하는 단위. 운영 홈페이지는 기본적으로 `main` 브랜치를 사용한다.
* Pull: GitHub의 최신 파일을 현재 컴퓨터로 가져오는 작업
* Commit: 어떤 내용을 수정했는지 변경 이력으로 기록하는 작업
* Push: 로컬에서 기록한 변경 사항을 GitHub에 올리는 작업
* GitHub Pages: 저장소의 홈페이지 파일을 인터넷에 공개하는 기능
* GitHub Actions: 엑셀 변환이나 홈페이지 배포처럼 정해진 작업을 자동으로 수행하는 기능

작업을 시작하기 전에는 반드시 pull하여 최신 상태를 확보한다. 여러 사람이 서로 다른 컴퓨터에서 동시에 수정하면 충돌이 발생할 수 있으므로, 작업 중인 사람이 있는지 먼저 확인하는 것이 안전하다.

### 0.4 현재 홈페이지 주소가 연결되는 원리

홈페이지의 공식 주소는 다음과 같다.

`https://nam-jin.uos.ac.kr`

그러나 홈페이지 파일 자체가 서울시립대학교 서버에 직접 저장된 것은 아니다. 실제 홈페이지 파일은 GitHub 저장소에 있으며, GitHub Pages가 이를 웹사이트로 제공한다.

전체 연결 구조는 다음과 같다.

`nam-jin.uos.ac.kr`(사이트 간판)
→ 서울시립대학교 DNS의 CNAME 설정(저 링크로 들어오면 '여기'로 보내주세요)
→ `dockzone22.github.io`(방금 그 '여기')
→ SURD Lab GitHub Pages 홈페이지(도착!)

각 요소의 역할은 다음과 같다.

* `nam-jin.uos.ac.kr`: 방문자가 사용하는 공식 홈페이지 주소
* DNS: 해당 주소로 접속한 방문자를 어느 서버로 보낼지 알려주는 인터넷 주소 체계
* CNAME: `nam-jin.uos.ac.kr`을 GitHub Pages 주소로 연결하는 DNS 정보
* TXT 레코드: 해당 GitHub 계정이 학교 도메인을 사용할 권한을 부여받았음을 확인하는 인증 정보(github>오른쪽 위 계정 클릭>settings>왼쪽 중하단 pages>add a domain)
* GitHub Pages Custom domain: 해당 저장소의 홈페이지를 `nam-jin.uos.ac.kr`이라는 주소로 제공하도록 지정하는 설정
* HTTPS: 홈페이지와 방문자 사이의 통신을 암호화하는 보안 연결

따라서 도메인 연결에는 학교 전산 담당자의 DNS 설정과 GitHub의 Custom domain 설정이 모두 필요하다. 어느 한쪽만 정상이어도 홈페이지가 제대로 연결되지 않을 수 있다.

도메인 관련 설정은 일반적인 콘텐츠 수정 과정에서는 건드리지 않는다.
추가로, github에서 repository 설정을 private로 변경할 시 사이트 공개가 막힌다.(다시 public으로 하면 열리긴 하겠으나, domain에 문제가 생기지 않을지는 본인도 모름)
public으로 설정했다는 것은 누구나 내 파일, 코드를 볼 수 있다는 뜻이므로
개인정보의 노출은 최대한 삼간다.

### 0.5 일반적인 홈페이지 수정 원칙

홈페이지의 텍스트와 목록은 가능한 한 기존 데이터 파일 또는 페이지별 콘텐츠 영역에서 수정한다. 화면 디자인을 담당하는 CSS나 공통 작동을 담당하는 JavaScript는 단순 콘텐츠 수정 목적으로 변경하지 않는다.

수정 작업은 다음 순서로 진행한다.

1. 어떤 페이지의 어떤 내용을 수정할지 정리한다.
2. GitHub 저장소의 최신 내용을 pull한다.
3. 수정 전 상태를 확인한다.
4. Antigravity에 수정 범위와 보존할 요소를 명확히 전달한다.
5. 변경된 파일과 코드 차이를 확인한다.
(data.js를 약간 수정하는 수준이라면 antigravity를 사용하지 않아도 무방하다)
6. 로컬 미리보기에서 PC·모바일 화면을 점검한다.
(publication은 보안 문제로 인해 로컬 미리보기에서 보이지 않을 수 있다)
7. 문제가 없으면 commit 및 push한다.
8. GitHub Pages 배포 상태를 확인한다.
9. 공식 홈페이지에서 변경 내용을 다시 확인한다.

여러 항목을 한꺼번에 수정하기보다는, 하나 수정하고 commit and push --> 잘 되는지, 예상대로 되었는지 확인하고 다음 부분을 수정한다.
페이지 또는 작업 종류별로 나누어 반영하는 것이 좋다. Commit 메시지에는 수정 내용을 알아볼 수 있게 작성한다.

예시는 다음과 같다.

* `Update members information`
* `Add 2026 research project`
* `Update lab news`
* `Revise contact information`
* `Update publications data`

작은 수정을 가할 때(방금 말한 예시처럼, data.js의 가벼운 수정)는
로컬 환경해서 js 코드 수정한 뒤,
github에서 repository>add file>upload files>변경된 파일만 업로드(전부 업로드해도 변경사항이 없는 파일들은 그대로가 된다).
하단 comment changes에다가 뭐 했는지 적으면 된다.

### 0.6 추후 인수인계 방법

담당자가 변경될 때는 파일만 전달해서는 안 되며, 다음 항목을 함께 인계해야 한다.

1. GitHub 저장소 주소
2. 저장소 접근 권한
3. 홈페이지의 현재 브랜치 및 배포 방식
4. 공식 도메인 주소
5. 홈페이지 수정에 사용하는 컴퓨터의 저장소 위치
6. Antigravity에서 저장소를 불러오고 작업하는 방법
7. 페이지별 콘텐츠 수정 방법
8. Publications 엑셀 파일 수정 및 반영 방법
9. GitHub Pages와 GitHub Actions 확인 방법
10. 학교 도메인 담당 부서 또는 연락 경로
11. 최근 수정 내역과 현재 해결되지 않은 문제

새 담당자에게는 GitHub 계정 비밀번호를 전달하지 않는다. 새 담당자의 GitHub 계정을 저장소 협업자로 초대하는 방식으로 권한을 부여한다.
기존 담당자가 더 이상 홈페이지를 관리하지 않는다면 새 담당자의 접근과 배포 권한이 정상적으로 작동하는 것을 확인한 뒤 기존 권한을 정리한다.

실제 인수인계 시에는 새 담당자가 다음 작업을 직접 한 번 수행하도록 한다.

1. 저장소 pull
2. 시험용 문구 수정
3. 로컬 미리보기 확인
4. commit 및 push
5. GitHub Pages 배포 확인
6. 실제 홈페이지 반영 확인
7. 시험용 수정 내용 원상복구

이 과정을 완료해야 단순한 파일 전달이 아니라 실질적인 운영 인수인계가 끝난 것으로 본다.

### 0.7 문제가 발생했을 때의 기본 대응

문제가 발생하면 여러 파일을 동시에 수정하지 말고, 먼저 문제가 발생한 범위를 확인한다(F12).
antigravity에게 문제 진단을 맡기면 알아서 해결하는 경우가 대부분이다.

#### 수정 내용이 홈페이지에 보이지 않는 경우

다음 순서로 확인한다.

1. 수정 내용을 저장했는지 확인한다.
2. commit과 push가 완료됐는지 확인한다.
3. GitHub 저장소의 `main` 브랜치에 수정 내용이 올라갔는지 확인한다.
4. 저장소의 Actions 또는 Pages 화면에서 배포가 성공했는지 확인한다.
5. 배포 완료 후 몇 분 정도 기다린다(최대 10분정도 소요되는 것으로 보인다).
6. 브라우저를 강력 새로고침하거나 캐시를 삭제한다.
7. 시크릿 창 또는 다른 기기에서 접속해 본다.

#### 홈페이지 전체가 열리지 않는 경우

먼저 공식 도메인 문제와 GitHub Pages 문제를 구분한다.

1. `https://nam-jin.uos.ac.kr` 접속 여부를 확인한다.
2. GitHub Pages의 기본 주소로 접속해 본다.
3. 기본 주소는 열리는데 공식 도메인만 열리지 않으면 DNS·CNAME·HTTPS 문제일 가능성이 높다.
4. 기본 주소도 열리지 않으면 GitHub Pages 배포 또는 저장소 설정을 확인한다.
5. GitHub의 저장소 Settings → Pages에서 배포 상태와 Custom domain을 확인한다.
6. DNS 문제로 판단되면 학교 전산 담당자(내선번호 6612)에게 문의한다.

#### 특정 페이지만 깨지는 경우

1. 해당 페이지에서 마지막으로 수정한 파일을 확인한다.
2. 브라우저 개발자 도구의 Console에서 오류를 확인한다.
3. 파일명, 경로, 쉼표, 따옴표 및 괄호 누락을 확인한다.
4. 이미지가 보이지 않으면 파일 위치와 파일명의 대소문자, 확장자명 등을 확인한다.
5. 문제가 된 commit 직전의 정상 버전과 변경 내용을 비교한다.

#### Publications가 표시되지 않는 경우

1. 엑셀 파일의 열 이름과 시트 이름이 변경되지 않았는지 확인한다.
2. 표시할 행의 `display` 값이 `Y`인지 확인한다.
3. 엑셀에서 JSON으로 변환하는 작업이 성공했는지 확인한다.
4. GitHub Actions 실행 결과를 확인한다.
5. `publications.json`이 정상적으로 갱신되었는지 확인한다.
6. 브라우저 Console에서 데이터 로딩 오류를 확인한다.

#### 잘못된 내용이 배포된 경우

GitHub의 변경 이력을 확인하고 마지막 정상 버전으로 되돌린다. 다만 정상 파일까지 함께 삭제하거나 저장소 전체를 강제로 초기화하지 않는다.
원인과 복구 대상이 확실하지 않으면 추가 수정 전에 이전 담당자 또는 GitHub 사용 경험이 있는 사람에게 확인한다.
antigravity에게 문제를 확인해달라고 해도 좋다.

### 0.8 비상시 운영 원칙

홈페이지 오류가 발생해도 절대로 저장소 전체를 삭제하거나 새 저장소를 만들어 즉시 교체하지 않는다.
대부분의 문제는 마지막 변경 사항, 배포 설정 또는 도메인 연결 상태를 확인하면 복구할 수 있다.

비상시에는 다음 원칙을 따른다.

* 문제가 발생한 시점과 마지막 수정 내용을 기록한다.
* 추가 작업을 멈추고 현재 상태를 보존한다.
* GitHub의 마지막 정상 commit을 확인한다.
* 문제와 관련 없는 파일은 수정하지 않는다.
* 복구 전 저장소와 주요 데이터 파일의 사본을 확보한다.
* 도메인, DNS 및 GitHub Pages 설정을 임의로 삭제하지 않는다.
* 비밀번호나 인증정보를 메신저, 문서 또는 AI 대화창에 남기지 않는다.
* 복구 후 공식 주소와 GitHub Pages 기본 주소를 모두 시험한다.
* 복구 내용과 원인을 인수인계 문서에 기록한다.

가장 중요한 원칙은 “기존 구조를 보존하고, 수정 범위를 작게 나누며, 배포 전후를 직접 확인하는 것”이다.

--------------------------------------------------------------------------------
[공통] 콘텐츠 변경 작업의 기본 워크플로우
--------------------------------------------------------------------------------
모든 콘텐츠 변경 작업은 반드시 다음의 4단계 라이프사이클을 준수해야 합니다.

1단계. 최신 상태 동기화 (작업 전)
  - 터미널(CMD, PowerShell, Git Bash 등)을 켜고 프로젝트 폴더로 이동합니다.
  - 원격 저장소의 최신 커밋을 로컬로 가져옵니다:
    $ git pull origin main

2단계. 콘텐츠 수정 및 변환
  - 텍스트/데이터 수정: data.js 또는 html 파일을 텍스트 에디터로 수정합니다.
  - 논문(Excel) 수정: data/publications.xlsx 수정 후 변환 스크립트 실행:
    $ python scripts/convert_publications.py
    (※ 실행에 pandas 및 openpyxl 라이브러리가 필요합니다.)

3단계. 로컬 테스트 및 브라우저 검증 (CORS 에러 예방)
  - 브라우저 보안 정책 상 file:/// 프로토콜(파일 더블 클릭)로 직접 실행하면
    논문 데이터 로드 시 "Failed to fetch" 오류가 발생합니다.
  - 반드시 파이썬 가상 서버를 띄워 로컬 웹 서버 환경에서 확인해야 합니다:
    $ python -m http.server 8000
  - 브라우저를 열고 http://localhost:8000/ 에 접속하여 디자인, 링크, 데이터를
    최종 검증합니다.

4단계. 커밋 및 원격 저장소 배포
  - 변경 내역 확인:
    $ git status
  - 스테이징 및 커밋:
    $ git add .
    $ git commit -m "feat: 업데이트 내용 요약"
  - 원격 저장소 push:
    $ git push origin main
  - GitHub Pages 배포 확인: 약 1분 이내에 배포가 완료되며 아래 주소에서 확인합니다.
    https://dockzone22.github.io/SURD-Lab/

이상의 작업들을 모두 antigravity가 대신 해줄 수 있다.
단, 먼저 google antigravity를 다운받아 본인 컴퓨터의 폴더(C:\Users\SmartCity20\.gemini\antigravity\scratch\surd-lab-homepage 이런 식으로)에
github repository에 업로드되어있는 내용을 pull 하여야 한다.
어떤 페이지의 어떤 부분을 수정하고자 하는지 명확한 예시를 들어 chatGPT, gemini, Claude 등에게 설명하고

  - 연구원 정보의 'interestsKr', 'interestsEn', 'nameKr', 'nameEn' 등을 수정합니다.
  - 김진하 박사님(연구교수) 정보는 'members.researchProfessor' 객체에서 직접 수정합니다.
* 삭제 방법
  - data.js의 해당 연구원 객체 블록을 삭제합니다.
  *주의*: 퇴직 혹은 졸업으로 구성원을 삭제할 때는 data.js의 데이터 객체를 삭제할 뿐
  아니라, assets/members/ 폴더의 사용되지 않는 구 사진 파일도 함께 삭제해 주어야
  저장소 용량을 절약할 수 있습니다.
* 이미지가 있을 경우 준비 규격과 교체 방법
  - 실제 폴더: assets/members/ 폴더 내에 인물별 사진을 업로드합니다.
  - 권장 규격: 1:1 정사각형 비율 (예: 300x300필셀) 프로필 형태의 이미지.(그냥 프로필 사진 3cm*4cm 등이어도 상관 없음)
  - 파일명 규칙: 소문자 영문명과 언더바 기법 사용 권장 (예: hocheol_yun.png)
  - 기본 이미지 처리: 사진이 준비되지 않은 연구원의 경우 image: ""로 비워두면,
    app.js가 initials(이니셜 텍스트)를 활용해 깔끔한 기본 원형 아바타를 띄웁니다.
* 정렬 및 화면 표시 규칙
  - 지도교수가 가장 상단에 크게 나타나고, 그 밑에 연구교수(김진하 교수), 그 밑에 박사과정
    그리드(phd-grid), 석사과정 그리드(masters-grid) 순으로 배치됩니다.
  - 각 그리드 내에서는 data.js 내 배열에 정의된 순서대로 카드들이 렌더링됩니다.
  - 실제 활용 데이터 필드: nameKr, nameEn, initials, roleKr, roleEn, interestsKr,
    interestsEn, image (외의 정의되지 않은 속성은 임의 추가 금지)
* 수정 예시 (data.js)
  {
    nameKr: "홍길동",
    nameEn: "Gildong Hong",
    initials: "GH",
    roleKr: "석사과정",
    roleEn: "M.S. Student",
    interestsKr: "도시재생, 공간 데이터 분석",
    interestsEn: "Urban Regeneration, Spatial Data Analytics",
    image: "./assets/members/gildong_hong.jpg"
  }
* 수정 후 확인 사항
  - 마우스를 카드 위에 올렸을 때(Hover) 뒷면 슬라이딩 오버레이에 관심 분야(Research Area)가
    깨짐 없이 적절하게 표출되는지 테스트합니다.
* 자주 발생하는 오류와 해결 방법
  - 현상: 새로 추가한 연구원 카드의 영문 직함이나 이니셜이 엉뚱한 사람과 겹칩니다.
  - 원인: 다른 연구원의 객체를 복사해서 붙여넣은 뒤 값을 전부 고치지 않았기 때문입니다.
  - 해결: 복사 붙여넣기 후 initials 및 nameEn 등의 세부 속성을 꼼꼼하게 다듬어 줍니다.

5. Publications (publications.html)
================================================================================
* 페이지의 역할
  - 엑셀 데이터를 바탕으로 구현된 학술 발표 논문 카탈로그 제공
* 주로 수정할 파일
  - data/publications.xlsx (★ 절대 HTML이나 JS 코드를 직접 수정 금지)
* 수정하면 안 되는 파일 또는 영역
  - scripts/convert_publications.py 및 publications.html 마크업
  - app.js 내의 비동기 fetch 렌더링 로직 및 CNAME, JSON 결과물 직접 편집
* 추가 방법
  - data/publications.xlsx 를 열고 'publications' 시트 내의 표 범위 내에 새 논문 데이터를
    행 추가하여 기입합니다. (display 컬럼 값을 'Y'로 해야 반영됩니다.)
* 기존 내용 수정 방법
  - 엑셀 내 수정할 논문 행의 데이터를 찾아 셀 내용을 수정한 뒤 저장합니다.
* 숨기기(N) 및 삭제 방법
  - 숨기기: 해당 논문 행의 display 값을 **N**으로 변경합니다.
  - 완전 삭제: 해당 논문 행 전체를 삭제(Delete Row)하여 표 크기를 줄여줍니다.
* 이미지가 있을 경우 준비 규격과 교체 방법
  - Publications 페이지는 이미지가 사용되지 않습니다.
* 정렬 및 화면 표시 규칙
  - 최신 연도순(year 내림차순) 정렬 후, 동일 연도 내에서는 sort_order 오름차순 정렬됩니다.
  - sort_order가 비어 있는 결측 데이터는 해당 연도 가장 마지막에 순서가 보존됩니다.
  - DOI가 있으면 DOI 버튼을, DOI는 없으나 URL이 존재하면 Link 버튼을 띄우고 둘 다
    없으면 버튼 링크를 출력하지 않습니다. (외부 링크는 새 탭으로 실행됨)
  - volume(issue)이 정상 조인되며 결측 필드로 인해 불필요한 마침표/쉼표가 남지 않습니다.
* 수정 예시 (엑셀 테이블 입력 규격)
  - id: PUB-131
  - type: Journal
  - type_index: SSCI (SSCI, SCIE, KCI, Other, Unverified, Not applicable 중 선택)
  - year: 2026
  - display: Y
  - sort_order: 1
* 수정 후 확인 사항
  - 로컬/GitHub Actions에 의해 빌드된 data/publications.json 파일 내에 수정본이
    정상 반영되었는지 체크하고, 화면 필터(SSCI/SCIE, KCI, Other) 분류 동작을 테스트합니다.
* 자주 발생하는 오류와 해결 방법
  - 현상: 새 논문을 입력하고 갱신했는데 웹페이지에서 전혀 보이지 않습니다.
  - 원인: display 컬럼 값을 'Y'로 쓰지 않았거나, 엑셀 표 범위 밖에 데이터를 적었을 때.
  - 해결: display 열을 'Y' 대문자로 지정하고, 해당 행이 PublicationsTable 범위에
          포함되어 있는지 엑셀 디자인 탭에서 확인합니다.

6. Alumni (alumni.html)
================================================================================
* 페이지의 역할
  - 졸업 동문들의 연도별/학위별 졸업 정보 및 총 동문 카운트 제공
* 주로 수정할 파일
  - data.js (alumni 배열)
* 수정하면 안 되는 파일 또는 영역
  - alumni.html 내의 뼈대 마크업 및 동적 인원수 카운트 스팬 태그
* 추가 방법
  - data.js의 'alumni' 배열에 새 졸업생 객체 블록을 추가합니다.
* 기존 내용 수정 방법
  - 성명(nameKr), 영문명(nameEn - 공백 시 "" 지정), 현재 랩 상주 여부(currentMember),
    학위 정보(degrees 배열 내 degreeKr, degreeEn, gradYear)를 편집합니다.
* 삭제 방법
  - data.js 의 동문 객체 블록을 삭제합니다.
* 이미지가 있을 경우 준비 규격과 교체 방법
  - Alumni 페이지는 동문 사진이 렌더링되지 않습니다.
* 정렬 및 화면 표시 규칙
  - 정렬 기준: 최종 학위 취득 연도(박사 연도 우선, 없으면 석사 연도) 기준 최신순 정렬.
  - 동명이인 식별 및 처리:
    - 동문 명단 중 동명이인(예: 이지현 동문)이 여러 명 존재할 수 있습니다.
    - data.js 내에는 학번이나 주민번호 같은 고유 키가 없으므로, **영문명(nameEn) 유무**와
      **degrees 내부의 졸업연도 및 학위 내역**을 세밀히 보고 구별해야 합니다.
    - 섣부르게 성함만 보고 통합 카드로 합치거나 삭제하는 행위는 절대 금지합니다.
  - 석·박사 통합 동문 학위 처리:
    - 한 동문이 SURD Lab에서 석사와 박사를 모두 취득한 경우, 하나의 카드로 통합하여
      degrees 내부에 2개 학위 정보를 기입합니다.
    -degrees 배열에 넣는 순서와 상관없이, app.js가 렌더링할 때 무조건 **박사(Ph.D.)가
     상단, 석사(M.S.)가 하단**에 오도록 정렬하여 깔끔한 포맷으로 출력해 줍니다.
* 수정 예시 (data.js)
  {
    nameKr: "이정현",
    nameEn: "Junghyun Lee",
    currentMember: true,
    degrees: [
      { degreeKr: "공학석사", degreeEn: "M.S.", gradYear: "2020" },
      { degreeKr: "공학박사", degreeEn: "Ph.D.", gradYear: "2026" }
    ]
  },
* 수정 후 확인 사항
  - Alumni 페이지 최상단 우측에 동문 총인원수 '총 124명 (124)' 등의 텍스트가 괄호 및
    오타 없이 실시간 동적 계산되어 노출되는지 점검합니다.
* 자주 발생하는 오류와 해결 방법
  - 현상: 동명이인을 추가했더니 한 사람의 카드에 학위 3개가 합쳐져 렌더링됩니다.
  - 원인: 이름(nameKr)을 매칭하는 함수가 없고, 단순히 data.js 배열 내 객체들을 1:1로
          그대로 렌더링하기 때문입니다. 누군가 객체를 실수로 지우고 합쳤을 가능성이 큽니다.
  - 해결: 백업본을 찾아 개별 독립된 객체로 다시 쪼개어 기재해 줍니다.

7. News (news.html)
================================================================================
* 페이지의 역할
  - 연구실의 기쁜 소식(Lab News) 및 교수님 언론 보도(Interview/기고문) 수록
* 주로 수정할 파일
  - data.js (news 및 interviews 배열)
* 수정하면 안 되는 파일 또는 영역
  - news.html 내의 탭 토글 제어 영역 및 app.js 의 initNewsTabs() 기능
* 추가 방법
  - Lab News 추가: news 배열 가장 윗줄(인덱스 0)에 객체를 삽입합니다.
  - Interview 추가: interviews 배열 상단에 인터뷰 객체 블록을 추가합니다.
* 기존 내용 수정 방법
  - 날짜(date), 한글/영문 제목, 상세설명(descKr, descEn), 매체(source), 링크(url) 편집.
* 삭제 방법
  - Lab News 삭제: news 배열에서 원하지 않는 객체를 삭제합니다.
    (※ 최대 10개만 유지하는 운영 원칙을 둡니다. 최신 뉴스를 0번째에 추가할 때마다,
    가장 아래에 있는 11번째 객체 1개를 제거하여 10개 한도를 항시 조율합니다.)
  - Interview 삭제: 인터뷰와 기고문은 대외 홍보 자료이므로 **원칙적으로 삭제 금지**합니다.
* 이미지가 있을 경우 준비 규격과 교체 방법
  - 뉴스 관련 세부 사진은 사용되지 않으며, 카드로 구성되어 텍스트 정보만 렌더링됩니다.
* 정렬 및 화면 표시 규칙
  - Lab News: news 배열의 0~2번째(최신 3개)가 메인 화면 최근 소식과 자동 연동됩니다.
  - Interview: type 값("interview" 또는 "column" 소문자 기입 필수)에 의해 좌측 뱃지의
    카테고리 색상 클래스가 적용됩니다. 클릭 시 새 창('_blank')으로 링크 이동합니다.
  - 두 항목은 data.js 내에 **완전히 독립된 별개의 2개 배열**로 선언되어 있습니다.
* 수정 예시 (data.js)
  interviews: [
    {
      date: "2026.07.22",
      type: "interview", // "interview" 또는 "column" (소문자!)
      titleKr: "도시 쇠퇴와 스마트재생 인터뷰",
      titleEn: "Urban Decline and Smart Renewal Interview",
      description: "교수님 기고문 요약 내용",
      source: "서울일보",
      url: "https://example.com/news/123"
    }
  ]
* 수정 후 확인 사항
  - 인터뷰 탭의 "원문 보기"를 클릭했을 때 브라우저 팝업 차단 없이 새 탭에서 잘 열리는가?
* 자주 발생하는 오류와 해결 방법
  - 현상: 신규 인터뷰 카드의 뱃지 영역이 빈 텍스트로 보이고 흰색으로 표시됩니다.
  - 원인: type 속성값에 "interview" 가 아닌 "INTERVIEW" 등 대문자를 기입했기 때문입니다.
  - 해결: 소문자 "interview" 또는 "column"으로 텍스트를 정정합니다.

8. Contact (contact.html)
================================================================================
* 페이지의 역할
  - 연구실 오시는 길, 대중교통 정보 및 지도 정보 안내
* 주로 수정할 파일
  - data.js (contact 객체 데이터 정보)
  - contact.html (Google Maps iframe 소스 코드 및 외부 바로가기 링크)
* 수정하면 안 되는 파일 또는 영역
  - contact.html 의 CSS 클래스 및 버튼 레이아웃 구조
* 추가 방법
  - 대중교통이나 설명 줄 추가는 data.js contact 객체의 한글/영문 텍스트 내에서 개행
    태그(<br>)를 사용하여 추가적으로 기입하면 동적 렌더링에 편입됩니다.
* 기존 내용 수정 방법
  - 이메일, 전화번호, 연구실 위치(315호) 텍스트 등은 data.js 내의 'contact' 객체 값을
    수정하면 메인 헤더 드롭다운 및 contact.html 화면으로 일괄 동적 반영됩니다.
  *주의*: 구글 지도는 contact.html 파일에 직접 iframe으로 기입되어 있으므로, 검색
  쿼리 정보('q=서울시립대학교+배봉관' 및 'query=서울시립대학교+배봉관')와 교수님 연구실
  위치 설명 텍스트('배봉관 301호')는 **contact.html 내에서 직접 찾아 수동 수정**해야 합니다.
* 삭제 방법
  - data.js의 contact.tel 속성을 지우거나 빈 문자열로 두면, app.js가 전화번호 영역을
    화면에서 자동적으로 완전히 숨겨 숨김 처리를 지원합니다.
* 이미지가 있을 경우 준비 규격과 교체 방법
  - 지도는 구글 맵 iframe 방식으로 렌더링되므로 별도의 정적 이미지는 사용하지 않습니다.
* 정렬 및 화면 표시 규칙
  - 모바일 반응형 디자인 모드에서 지도가 가로 너비를 꽉 채우도록 반응형 구현되어 있습니다.
* 수정 예시 (contact.html)
  <iframe
    src="https://www.google.com/maps?q=새로운+빌딩+위치&output=embed"
    ...
  </iframe>
* 수정 후 확인 사항
  - 수정한 이메일 정보가 메인화면 헤더 우측 'Quick Info' 호버 시에도 잘 연동되는가?
* 자주 발생하는 오류와 해결 방법
  - 현상: 지도가 화면 크기에 상관없이 작게 뭉개집니다.
  - 원인: contact.html iframe의 width 값을 임의의 픽셀(px)로 고정했기 때문입니다.
  - 해결: width="100%", height="100%"를 적용하고 컨테이너 비율 스타일을 타게 합니다.

  - 6단계: 인수인계가 최종 확인되면, 기존 담당자의 권한은 Collaborators 목록에서

10.3 GitHub를 이용한 정상 버전 복구 (롤백 가이드)
  - 문제가 생겼을 때 전체 파일을 과거 버전으로 무식하게 복사하여 덮어쓰거나, 저장소를
    삭제하고 다시 파는 행위는 심각한 꼬임 문제를 야기하므로 절대 금지합니다.
  - 1단계: 문제가 발생한 시점과 원인이 되는 코드를 파악합니다.
  - 2단계: 터미널에서 마지막 정상 동작했던 커밋 ID를 확인합니다:
          $ git log --oneline
  - 3단계: 정상 작동했던 커밋과 현재의 특정 파일 차이점을 검사합니다:
          $ git diff [커밋ID] -- data.js
  - 4단계: 문제가 생긴 특정 파일만 정상 상태로 되돌립니다:
          $ git restore --source=[커밋ID] data.js
  - 5단계: 로컬 간이 서버에서 해당 복구본이 작동하는지 직접 확인합니다.
  - 6단계: 복구 내용을 새로운 커밋으로 생성하고 push 합니다:
          $ git commit -m "fix: Restore data.js to commit [ID]"
          $ git push origin main

10.4 상황별 복구 절차 및 문제 해결 가이드
  - 잘못된 문구가 배포된 경우: data.js 또는 HTML을 수정하고, 로컬 서버 확인 후 push.
  - JS 문법 오류로 데이터가 출력되지 않는 경우: 브라우저 콘솔(F12)을 켜고 구문 에러가 난
    라인 번호(예: 끝에 누락된 콤마 등)를 찾아 data.js 수정.
  - 이미지가 보이지 않는 경우: assets/members/ 폴더 내에 실제 파일명이 대소문자까지
    정확하게 일치하는지 대조 (경로 오타 수정).
  - Excel 변환 후 논문 목록이 공백인 경우: data/publications.json을 열어 배열이 비어
    있는지 확인. excel_path 경로 불일치 시 스크립트 실행 디렉토리 교정.
  - Actions / Pages 배포가 실패한 경우: GitHub Actions 탭의 실패 로그(Red Cross)를
    열어 쉘 스크립트 문법이나 엑셀 표 범위 이탈 오류 메시지를 식별하고 엑셀 재조정.
  - 도메인 접속 불가 (Pages 기본 주소는 접속됨): 학교 DNS CNAME이 유실되었거나, 루트의
    CNAME 파일이 지워졌을 가능성이 큼. 저장소에 CNAME 파일이 잘 들어있는지 확인.
  - 동시 수정으로 충돌(Conflict)이 났을 경우: git status로 충돌 파일 확인 후, 에디터에서
    <<<<<<< 와 >>>>>>> 마커를 확인해 올바른 코드로 수동 병합 후 다시 add 및 push 진행.
