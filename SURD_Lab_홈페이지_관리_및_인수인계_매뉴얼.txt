0. 이 문서의 목적과 사용 방법
================================================================================

0.1 인수인계 목적

이 문서는 SURD Lab 홈페이지의 내용을 안전하게 추가, 수정, 삭제하는 방법을 설명한다.
후임자가 새 홈페이지를 제작하는 것이 아니라, 현재 홈페이지의 구조와 디자인을 유지하면서
연구실 정보를 정확하게 갱신하는 것이 목적이다.

특별한 이유와 담당자의 승인이 없으면 다음 요소를 변경하지 않는다.

- 전체 페이지 구성과 메뉴 순서
- 헤더, 푸터와 모바일 메뉴
- 홈페이지의 색상, 글꼴과 디자인 체계
- PC와 모바일 반응형 구조
- 각 페이지의 기본 레이아웃
- data.js의 기존 필드명과 데이터 연결 방식
- GitHub Pages와 Custom domain 설정
- CNAME과 GitHub Actions 설정

구조나 디자인 변경이 필요하면 원본을 바로 배포하지 않는다. 로컬 환경 또는 별도 작업
브랜치에서 시험하고, 담당자가 화면을 확인한 뒤 반영한다.


0.2 이 문서의 정렬 기준

본문은 홈페이지 메뉴 순서에 맞춰 정리한다.

Home → About → Research → Members → Publications → Alumni → News → Contact

비전공자는 data.js 내부 순서보다 “어느 페이지를 수정하려는가”를 기준으로 찾는 편이 쉽다.
따라서 페이지별 안내에서 관련 data.js 위치를 함께 설명하고, 별도의 파일 지도도 제공한다.


0.3 가장 중요한 네 가지 원칙

1. 작업 전에는 GitHub의 최신 버전을 가져오고 수정 전 자료를 백업한다.
2. Antigravity, ChatGPT, Claude의 답변은 초안으로 취급하고 변경 파일과 실제 화면을 확인한다.
3. 로컬 화면을 확인하고 담당자의 승인을 받기 전에는 commit이나 push를 하지 않는다.
4. 개인정보, 비밀번호, 인증번호, 토큰과 비공개 원자료를 AI 대화창이나 공개 저장소에 넣지 않는다.


0.4 10분 빠른 시작

1. SURD-Lab 로컬 폴더를 연다.
2. git status --short를 실행한다. 아무것도 표시되지 않아야 안전하다.
3. git pull --ff-only origin main으로 최신 버전을 가져온다.
4. 이 문서에서 수정하려는 페이지를 찾는다.
5. data.js, publications.xlsx 또는 해당 HTML 파일을 수정한다.
6. python -m http.server 8000으로 로컬 서버를 실행한다.
7. http://localhost:8000에서 PC와 모바일 화면을 확인한다.
8. git diff로 실제 변경 내용을 확인한다.
9. 담당자의 검토가 끝난 뒤 필요한 파일만 commit하고 push한다.
10. GitHub Actions와 공식 홈페이지에서 최종 결과를 확인한다.

*antigravity 에이전트를 활용하면 더 쉬울 수 있다. 위 텍스트를 붙여넣기하여도 무방할 것이라고 보임

1. 홈페이지와 파일의 기본 개념

1.1 SURD Lab 홈페이지의 형태

SURD Lab 홈페이지는 정적 웹사이트다. 별도의 관리자 화면이나 데이터베이스가 없으며,
GitHub 저장소에 있는 HTML, CSS, JavaScript, 이미지와 데이터 파일이 홈페이지를 만든다.

파일별 역할은 다음과 같다.

- HTML: 각 페이지의 뼈대와 고정 문구
- style.css: 색상, 글꼴, 간격과 반응형 디자인
- app.js: data.js의 내용을 화면에 표시하고 탭과 버튼을 작동시키는 기능
- data.js: 연구실 소개, 연구과제, 구성원, 동문, 뉴스와 연락처 데이터
- data/publications.xlsx: Publications 페이지의 편집 원본
- data/publications.json: 엑셀을 홈페이지가 읽을 수 있도록 변환한 결과
- scripts/convert_publications.py: publications.xlsx를 publications.json으로 변환하는 스크립트
- assets 폴더: 프로필 사진과 배경 이미지
- .github/workflows 폴더: 자동 변환과 배포 작업
- CNAME: nam-jin.uos.ac.kr 도메인 연결 정보


1.2 data.js를 이해하는 최소한의 지식

data.js는 홈페이지에 표시할 내용을 모아 둔 파일이다.

- 대괄호 [ ]: 여러 항목의 목록
- 중괄호 { }: 한 항목의 정보 묶음
- 콜론(:): 항목명과 값의 연결
- 쉼표 ,: 다음 항목이 이어짐
- 큰따옴표 " ": 글자 데이터

예시

news: [
  {
    date: "2026.10.13",
    titleKr: "새 소식",
    titleEn: "New Update"
  },
  {
    date: "2026.09.01",
    titleKr: "이전 소식",
    titleEn: "Previous Update"
  }
]

괄호나 쉼표 하나가 빠지면 data.js 전체를 읽지 못해 여러 페이지가 동시에 비어 보일 수 있다.
새 항목을 만들 때는 같은 배열의 정상 항목 전체를 복사한 뒤 값만 바꾸는 방법이 안전하다.


1.3 홈페이지 주소가 연결되는 원리

nam-jin.uos.ac.kr
→ 서울시립대학교 DNS의 CNAME 설정
→ dockzone22.github.io
→ SURD-Lab 저장소 main 브랜치의 GitHub Pages 홈페이지

각 요소의 역할은 다음과 같다.

- nam-jin.uos.ac.kr: 방문자가 사용하는 공식 주소
- DNS: 해당 주소를 어느 서버로 연결할지 알려주는 체계
- CNAME: 공식 주소를 GitHub Pages 주소로 연결하는 DNS 정보
- TXT 레코드: GitHub 계정이 학교 도메인을 사용할 권한이 있음을 확인하는 인증 정보
- Custom domain: GitHub Pages가 nam-jin.uos.ac.kr을 공식 주소로 사용하도록 하는 설정
- HTTPS: 홈페이지와 방문자 사이의 통신을 암호화하는 연결

일반적인 콘텐츠 수정에서는 DNS, CNAME, Custom domain과 HTTPS 설정을 건드리지 않는다.


1.4 공개 저장소라는 점

SURD-Lab 저장소는 홈페이지 공개를 위해 누구나 볼 수 있는 상태로 운영된다.
화면에서 숨긴 값, HTML 주석, data.js 값과 Excel 셀도 외부에서 확인할 수 있다.
파일을 나중에 삭제하더라도 이전 Git 기록에 남을 수 있다.

***따라서 공개하면 안 되는 자료(개인정보, 용역 보안사항 등)는 저장소에 처음부터 넣지 않는다!!!***

2. 계정과 작업환경 준비
================================================================================

2.1 필요한 계정과 프로그램

[필수]

- 개인 GitHub 계정: 저장소 접근, 변경 기록과 배포
- Git 또는 Git Bash: pull, diff, commit과 push
- Python: 로컬 서버 실행과 Publications 변환

[권장]

- Visual Studio Code: 파일 편집과 변경 내용 확인
- Google Antigravity: 로컬 저장소 분석, 코드 수정과 테스트
- ChatGPT 또는 Claude: 요구사항 정리, 프롬프트 작성, 설명과 교차검증

GitHub 계정 비밀번호를 넘겨주지 않는다. 후임자는 자신의 계정을 사용하고 기존 관리자가
Collaborator로 초대한다.


2.2 GitHub 저장소 권한 받기

1. 후임자가 자신의 GitHub 계정을 만든다.
2. 기존 관리자가 저장소 Settings의 Collaborators에서 후임자를 초대한다.
3. 후임자가 이메일 또는 GitHub 알림에서 초대를 수락한다.
4. 후임자에게 Write 이상의 권한이 있는지 확인한다.
5. 비밀번호, 개인 액세스 토큰, SSH Private Key와 인증번호는 공유하지 않는다.


2.3 저장소를 처음 내려받기

Git Bash 또는 터미널에서 다음 명령을 실행한다.

git clone https://github.com/dockzone22/SURD-Lab.git
cd SURD-Lab
git status
git remote -v
git branch --show-current

정상 상태는 다음과 같다.

- 현재 브랜치가 main이다.
- 원격 저장소 주소가 dockzone22/SURD-Lab이다.
- 커밋되지 않은 변경 사항이 없다.

로컬 폴더는 담당자가 찾기 쉬운 위치에 둔다. OneDrive 등 실시간 동기화 폴더에서는
Git 파일과 동기화 프로그램이 충돌할 수 있으므로 가능하면 별도 작업 폴더를 사용한다.


2.4 Antigravity에서 저장소 열기

1. Antigravity를 실행한다.
2. Open Folder 또는 폴더 열기를 선택한다.
3. clone한 SURD-Lab 폴더 전체를 연다.
4. 작업 전에 저장소 구조와 관련 파일을 먼저 읽고 보고하도록 요청한다.
5. 프롬프트 끝에는 “로컬 수정과 검증까지만 진행하고 commit과 push는 하지 말 것”이라고 쓴다.

한 작업 중에는 한 AI만 실제 파일을 수정하는 것이 안전하다. ChatGPT와 Claude는 문안이나
diff 검토에 사용하고, 여러 AI가 같은 로컬 폴더를 동시에 고치지 않게 한다.


2.5 로컬 홈페이지 실행

HTML 파일을 더블클릭하면 Publications처럼 fetch를 사용하는 기능이 작동하지 않을 수 있다.
저장소 폴더에서 다음 명령을 실행한다.

python -m http.server 8000

Windows에서 python 명령을 찾지 못하면 다음 명령을 사용한다.

py -m http.server 8000

브라우저에서 다음 주소를 연다.

http://localhost:8000

서버를 종료하려면 터미널에서 Ctrl+C를 누른다.

3.1 AI 도구별 역할

[Antigravity]

- 로컬 파일 검색
- 코드 수정
- 로컬 미리보기와 오류 진단
- 실제 파일을 바꿀 수 있으므로 수정 범위와 push 금지를 명시해야 함

[ChatGPT]

- 요구사항 정리
- Antigravity에 전달할 프롬프트 작성
- 코드나 문안 설명
- 변경 내용 검토와 교차검증

[Claude]

- 긴 코드나 문서의 독립 검토
- 다른 해결안 비교
- 전체 원자료보다 필요한 코드와 익명화된 자료만 제공


3.2 AI에 입력하지 말아야 할 정보

- GitHub 비밀번호, 개인 액세스 토큰, SSH Private Key
- 이메일 인증번호, 복구 코드와 2단계 인증 정보
- 학생과 졸업생의 개인 전화번호, 개인 이메일과 주소
- 생년월일, 학번, 주민등록번호와 계좌정보
- 공개 전 논문, 심사 자료, 연구비 내부자료와 계약서
- 정보공개가 제한된 연구자료
- 사용 동의를 확인하지 않은 고해상도 인물 사진 원본
- 계정이나 토큰이 표시된 브라우저와 터미널 전체 화면

AI 검토가 필요하면 이름을 A, B로 바꾸고 연락처를 삭제한 사본을 만든다. 코드 오류만
확인하려면 저장소 전체나 원자료를 올리지 말고 관련 함수와 오류 메시지만 제공한다.


3.3 홈페이지 개인정보 원칙

1. 실제 홈페이지에 공개할 정보만 data.js와 publications.xlsx에 넣는다.
2. 화면에서 표시하지 않는 값도 브라우저와 공개 저장소에서 볼 수 있다고 가정한다.
3. 구성원 사진, 소속과 약력은 본인 또는 연구실의 공개 동의를 확인한다.
4. 졸업생 원자료와 연락처 명단은 저장소 밖의 접근 제한 공간에 보관한다.


3.4 개인정보나 비밀정보를 잘못 올린 경우

1. 추가 push와 공유를 즉시 멈춘다.
2. 비밀번호나 토큰이면 즉시 폐기하고 새 값으로 바꾼다.
3. 노출된 파일명과 commit ID를 기록한다.
4. 현재 파일에서 삭제하되 과거 Git 기록까지 사라졌다고 생각하지 않는다.
5. GitHub 기록 정리가 가능한 관리자나 경험자에게 도움을 요청한다.
6. 필요한 경우 정보 주체와 연구실 책임자에게 노출 범위와 조치 내용을 보고한다.
*거의 이럴 일, 이런 정보를 만질 일도 없다고 보는 것이 편하나, 혹시나 하는 상황 대비

3.5 AI에게 작업을 맡기는 기본 순서

1. 작업 목적과 수정할 페이지를 한 문장으로 정한다.
2. 먼저 관련 파일과 기존 데이터 구조를 읽고 보고하도록 요청한다.
3. 수정 가능한 파일과 건드리면 안 되는 파일을 구분한다.
4. 기존 디자인, 데이터 필드, 정렬과 반응형 구조를 유지하도록 명시한다.
5. 확인되지 않은 이름, 소속, 학위와 영문 문안을 만들지 말라고 한다.
6. 로컬에서 PC와 모바일 화면, 링크와 Console 오류를 확인하도록 한다.
7. 변경 파일과 diff를 보고받는다.
8. 담당자가 승인하기 전 commit과 push를 하지 말라고 한다.


3.6 AI 공통 프롬프트 기본형

SURD Lab 홈페이지 로컬 저장소에서 [페이지]의 [항목]을 수정해줘.

작업 전 관련 HTML, data.js, app.js, style.css의 현재 구조를 확인하고 수정 범위를 먼저
보고해줘. 기존 디자인, 데이터 필드, 정렬 순서와 반응형 구조를 유지하고 관련 없는 파일은
수정하지 말아줘. 확인되지 않은 개인정보나 영문 정보를 임의로 만들지 말아줘.

수정 후 로컬에서 데스크톱과 모바일 화면, Console 오류와 링크 동작을 확인해줘. 변경한
파일과 핵심 diff를 보고하되 commit과 push는 하지 말아줘.


3.7 AI 교차검증 방법

AI 여러 개가 같은 답을 했다는 이유만으로 정확하다고 판단하지 않는다. 한 AI가 수정안을
만들면 다른 AI에는 원본 요구사항, 변경 diff와 테스트 결과를 주고 다음만 확인하게 한다.

- 요청 범위를 벗어난 수정이 있는가
- 개인정보나 내부자료가 포함되었는가
- 기존 데이터 구조와 다른 필드를 만들었는가
- PC와 모바일에 부작용이 생길 가능성이 있는가
- 더 작은 수정으로 해결할 수 있는가

최종 판단 기준은 다수결이 아니라 기존 코드, 원자료와 실제 로컬 화면이다.


================================================================================
4. 모든 수정 작업의 표준 절차
================================================================================

4.1 작업 전 확인

[ ] 다른 사람이 같은 저장소를 수정 중인지 확인했다.
[ ] 수정할 페이지와 공개 문안을 담당자에게 확인했다.
[ ] 사진과 개인정보의 공개 가능 여부를 확인했다.
[ ] 대규모 수정이면 저장소와 원자료를 별도 위치에 백업했다.


4.2 최신 상태 동기화

git status --short

결과가 비어 있으면 다음을 실행한다.

git pull --ff-only origin main

git status --short에 파일명이 표시되면 아직 저장하지 않은 로컬 변경이 있다는 뜻이다.
이 상태에서 pull하거나 AI 수정을 계속하지 말고 변경한 사람과 내용을 먼저 확인한다.
파일을 삭제하거나 강제로 초기화해서 해결하지 않는다.


4.3 수정 범위를 작게 나누기

한 번에 여러 페이지를 수정하면 오류 원인을 찾기 어렵다. 다음 작업은 따로 진행한다.

- 구성원 정보 수정
- 연구과제 추가
- 뉴스 추가
- 논문 갱신
- 디자인 변경

각 작업마다 로컬 검증과 commit을 끝낸 뒤 다음 작업을 시작한다.


4.4 변경 내용 확인

git status --short
git diff
git diff --check

특정 파일만 확인하려면 다음처럼 실행한다.

git diff -- data.js

확인 사항

- 예상한 파일만 바뀌었는가
- 이름, 날짜, 영문명, 링크와 이미지 경로가 원자료와 일치하는가
- 괄호, 쉼표와 따옴표가 빠지지 않았는가
- AI가 관련 없는 코드나 스타일을 정리하지 않았는가
- 개인정보, 토큰과 로컬 경로가 포함되지 않았는가


4.5 로컬 검증

1. python -m http.server 8000으로 로컬 서버를 실행한다.
2. 수정한 페이지를 넓은 PC 화면에서 확인한다.
3. 브라우저 창을 줄이거나 개발자 도구를 이용해 모바일 화면을 확인한다.
4. 한글과 영문 전환을 확인한다.
5. 탭, hover, 버튼과 외부 링크를 시험한다.
6. F12의 Console에 빨간 오류가 없는지 확인한다.
7. 메인 페이지와 수정하지 않은 인접 페이지에도 이상이 없는지 확인한다.


4.6 commit과 push

로컬 결과를 담당자가 확인한 뒤에만 배포한다. git add .로 모든 파일을 올리기보다 실제로
수정한 파일을 지정한다.

예시

git add data.js
git diff --cached
git commit -m "Update alumni information"
git push origin main

Publications를 수정했다면 다음처럼 필요한 파일을 지정한다.

git add data/publications.xlsx data/publications.json

commit 메시지는 무엇을 수정했는지 알 수 있게 작성한다.

- Update members information
- Add 2026 research project
- Update lab news
- Revise contact information
- Update publications data
- Fix alumni card layout

- 파일명을 seoul_dark_40.png로 유지하면 코드 수정 없이 교체할 수 있다.

- 최근 소식 3개의 카드 높이와 줄바꿈이 정상인가
- 배경 이미지가 PC와 모바일에서 과도하게 잘리지 않는가

5.3 Research  research.html
--------------------------------------------------------------------------------

[페이지 역할]

연구실의 연구분야와 진행 중 또는 완료된 연구과제를 보여준다.

[주요 수정 위치]

- 연구분야 카드: SURD_DATA.research.areas
- 수행과제: SURD_DATA.research.projects

[연구과제 예시]

{
  titleKr: "과제명",
  titleEn: "Project Title",
  duration: "2026.03 ~ 2029.02",
  fundingKr: "발주처",
  fundingEn: "Sponsor",
  status: "ongoing"
}

[운영 방법]

- 진행 중 과제는 status: "ongoing"으로 입력한다.
- 완료 과제는 status: "completed"로 입력한다.
- status는 반드시 소문자 영문으로 입력한다.
- 과제 기간은 월 단위로 통일한다.
- 같은 계속과제의 연차별 기록을 별도 과제로 중복 등록하지 않는다.
- 최신 과제를 배열 위쪽에 둔다.
- NTIS를 근거로 작성했다면 현재 페이지의 자료 출처 표기를 유지한다.(NTIS 저작권 문제)
- 과제번호, 사업자등록번호, 세부 연구비와 내부자료는 화면뿐 아니라 data.js에도 넣지 않는다.(굳이 필요하지 않으며, 알 필요도 없다)

[확인 사항]

- ongoing과 completed 탭이 정확히 분류되는가
- 동일 과제가 중복 표시되지 않는가
- 기간, 발주처와 과제명이 공식 원자료와 일치하는가
- 출처 표기가 필요한 과제에 NTIS가 표시되는가

[구성원 예시]

{
  nameKr: "홍길동",
  nameEn: "Gildong Hong",
  initials: "GH",
  roleKr: "석사과정",
  roleEn: "M.S. Student",

[운영 방법]

- 새 구성원은 같은 과정의 기존 객체를 복사하고 모든 값을 확인한다.
- 사진은 1:1 정사각형 또는 인물 중심 이미지를 사용한다.
- 파일명은 소문자 영문과 언더바를 권장한다. 예: gildong_hong.jpg
- 사진이 없으면 image를 빈 문자열로 두고 initials를 입력한다.

- 사진 파일은 다른 페이지와 Alumni에서 사용하지 않는지 확인한 뒤 삭제한다.

[확인 사항]

- 이름, 영문명, 과정과 이니셜이 같은 사람의 정보인가
- 원형 사진이 찌그러지지 않는가
- hover 시 관심 분야가 잘리지 않는가
- 모바일에서도 카드 순서와 간격이 정상인가

5.5 Publications  publications.html
--------------------------------------------------------------------------------

[페이지 역할]

논문과 연구 성과를 연도 및 분류별로 제공한다.

[편집 원본]

data/publications.xlsx

Publications는 Excel만 수정한다. publications.html, app.js와 publications.json을 직접
수정하지 않는다.

[추가 또는 수정 절차]

1. data/publications.xlsx를 별도 위치에 백업한다.
2. publications 시트의 PublicationsTable 범위 안에 새 행을 추가한다.
3. 기존 행과 같은 형식으로 입력한다.
4. 공개할 행의 display 값을 대문자 Y로 입력한다.
5. 같은 연도 안의 순서를 sort_order로 정한다.
6. Excel을 저장한다.
7. 변환 스크립트를 실행한다.

python scripts/convert_publications.py

Windows에서 python 명령이 없으면 다음을 사용한다.

py scripts/convert_publications.py

8. data/publications.json이 갱신되었는지 확인한다.
9. 로컬 서버에서 필터, 정렬, DOI와 Link 버튼을 확인한다.
*로컬에서는 보안 문제로 보이지 않을 수 있다. push and commit 이후 반영된 것을 확인하는 게 편할 수도.
** 엑셀 파일만 잘 수정했다면 문제 없다.
[주요 규칙]

- 최신 연도순으로 표시된다.
- 같은 연도에서는 sort_order 오름차순으로 표시된다.
- display가 Y인 행만 공개된다.
- DOI가 있으면 DOI 버튼이 표시된다.
- DOI가 없고 URL이 있으면 Link 버튼이 표시된다.
- DOI와 URL이 모두 없으면 버튼이 표시되지 않는다.(이는 120개가 넘는 논문에 하나하나 하기에 시간이 오래 소요되어 하지 않았었다)
- 시트명, 열 이름과 PublicationsTable 이름을 임의로 변경하지 않는다.
- 행을 표 범위 밖에 입력하면 변환 대상에서 빠질 수 있다.

[자주 발생하는 오류]

논문이 보이지 않으면 다음을 확인한다.

1. display가 Y인가
2. 새 행이 PublicationsTable 범위 안에 있는가
3. 시트명과 열 이름이 바뀌지 않았는가
4. 변환 스크립트가 오류 없이 끝났는가
5. publications.json이 갱신되었는가
6. GitHub Actions가 성공했는가
7. F12 Console에 fetch 오류가 있는가

5.6 Alumni  alumni.html
--------------------------------------------------------------------------------

[페이지 역할]

졸업생을 학위별로 소개하고 동문 수를 보여준다.

[주요 수정 위치]

data.js의 alumni 배열

[기본 예시]

{
  nameKr: "이정현",
  nameEn: "Junghyun Lee",
  currentMember: false,
  degrees: [
    { degreeKr: "공학석사", degreeEn: "M.S.", gradYear: "2020" },
    { degreeKr: "공학박사", degreeEn: "Ph.D.", gradYear: "2026" }
  ]
}

[운영 방법]

- 한 사람이 연구실에서 석사와 박사를 모두 취득했다면 객체 하나에 두 학위를 기록한다.
- degreeKr과 degreeEn이 같은 학위를 뜻하는지 확인한다.
- 공학석사와 Ph.D.처럼 서로 다른 학위가 연결되어 있으면 원자료를 확인한다.
- 동명이인을 이름만 보고 합치거나 삭제하지 않는다.(이지현, 이정현이 그 사례)
- 동명이인은 영문명, 졸업연도와 학위 이력을 함께 대조한다.
- 박사학위가 있으면 박사 탭에 표시하고, 박사학위가 없이 석사학위만 있으면 석사 탭에
  표시하는 현재 분류 규칙을 유지한다.
- 최종 학위 취득연도 기준 최신순 정렬을 유지한다.
- 총 동문 수가 정확한지 확인한다.

[박사 프로필 카드가 적용된 경우]

현재 data.js의 정상 박사 객체와 app.js가 실제로 사용하는 필드를 먼저 확인한다. 구현된
필드에 맞춰 다음 정보를 관리한다.

- image: 프로필 사진 경로
- initials: 사진이 없을 때 표시할 이니셜
- affiliationKr, affiliationEn: 현재 소속
- positionKr, positionEn: 현재 직위
- bioKr, bioEn: 짧은 약력

사진이 없거나 로딩에 실패하면 원형 이니셜이 표시되어야 한다. 영문명이 없을 때 로마자
이니셜을 임의로 추측하지 말고 확인된 initials 값을 입력한다.

소속과 약력은 공개가 확인된 최신 정보만 사용한다. 개인 연락처와 비공개 경력 자료는
입력하지 않는다.

[확인 사항]

- 박사와 석사 탭 분류가 정확한가
- 석박사 학위가 있는 사람이 중복 카드로 만들어지지 않았는가
- 사진이 원형 안에서 찌그러지지 않는가
- 사진이 없을 때 이니셜이 표시되는가
- 박사 카드의 hover 약력이 잘리지 않는가
- 모바일에서는 탭 또는 약력 보기 기능이 작동하는가
- 전체 동문 수가 실제 객체 수와 일치하는가

5.7 News  news.html
--------------------------------------------------------------------------------

[페이지 역할]

연구실 소식과 교수 인터뷰 또는 기고문을 보여준다.

[주요 수정 위치]

- Lab News: data.js의 news 배열

두 배열은 서로 독립되어 있다.

[Interview 또는 Column 예시]

{

  titleKr: "인터뷰 제목",
  titleEn: "Interview Title",

  url: "https://example.com/article"
}

[운영 방법]

- 최신 항목을 배열 맨 위에 추가한다.
- type은 interview 또는 column을 소문자로 입력한다.
- Lab News의 최신 3개는 Home에도 표시된다.
- Lab News는 운영 편의를 위해 최신 10개를 유지한다.
- 오래된 News를 삭제하기 전 기록 보존 필요성을 확인한다.
- Interview와 Column은 대외 기록이므로 특별한 이유 없이 삭제하지 않는다.
- 기사 전문을 복사하지 말고 짧게 요약한다.
- 원문 링크와 매체 출처를 표시한다.

[확인 사항]

- Lab News와 Interview 탭이 정상적으로 전환되는가
- interview와 column 배지가 정확히 표시되는가
- 원문 보기 버튼 전체가 클릭되는가
- 링크가 새 탭에서 정상적으로 열리는가
- 카드 높이가 내용보다 작아 글이나 버튼이 잘리지 않는가

7.3 특정 파일만 안전하게 복구하기

문제가 생겼을 때 저장소 전체를 과거 상태로 강제 초기화하지 않는다. 마지막 정상 commit을
찾고 문제가 있는 파일만 복구한다.

git log --oneline -n 15
git diff <정상커밋ID> -- data.js
git restore --source=<정상커밋ID> -- data.js
git diff -- data.js

복구된 파일을 로컬에서 확인한 뒤 새 commit으로 기록한다.

사용 금지

- git reset --hard
- git push --force

위 명령은 정상 파일과 협업 기록까지 손상할 수 있다.


7.4 충돌이 발생한 경우

pull 또는 push 도중 conflict가 발생하면 추가 명령을 반복하지 않는다.

1. git status 결과를 저장한다.
2. 충돌한 파일명을 확인한다.
3. 동시에 작업한 담당자에게 알린다.
4. Antigravity 또는 Git 경험자에게 현재 status와 diff를 보여주고 병합 방법을 확인한다.
5. <<<<<<<, =======, >>>>>>> 표시를 무작정 삭제하지 않는다.
6. 병합 후 로컬 화면과 Console을 다시 확인한다.

8. 문제 발생 시 기본 대응
================================================================================

8.1 F12 개발자 도구 사용

1. 문제가 보이는 페이지에서 F12를 누른다.
2. Console 탭을 연다.
3. 빨간 오류의 첫 메시지, 파일명과 줄 번호를 기록한다.
4. 필요한 오류 메시지만 AI 또는 담당자에게 전달한다.
5. 원인을 확인하기 전 여러 파일을 동시에 수정하지 않는다.


8.2 수정 내용이 홈페이지에 보이지 않는 경우

1. 파일을 저장했는지 확인한다.
2. git status로 로컬 변경 상태를 확인한다.
3. commit과 push가 성공했는지 확인한다.
4. GitHub main 브랜치의 최신 commit을 확인한다.
5. Actions와 Pages 배포가 성공했는지 확인한다.
6. 수 분 기다린 뒤 Ctrl+F5로 새로고침한다.
7. 시크릿 창 또는 다른 기기에서 접속한다.


8.3 여러 페이지의 데이터가 동시에 사라진 경우

가능성이 높은 원인은 data.js 문법 오류다.

- F12 Console의 첫 오류를 확인한다.
- 오류 줄 주변의 따옴표, 쉼표, 대괄호와 중괄호를 확인한다.
- 마지막 정상 commit의 data.js와 비교한다.
- 오류를 모르면 진단만 요청하고 임의 수정 범위를 넓히지 않는다.


8.4 이미지가 보이지 않는 경우

- data.js의 경로와 실제 파일 위치가 같은가
- 파일명의 대문자와 소문자가 일치하는가
- 확장자가 jpg, jpeg, png 중 무엇인가
- 파일명이 한글이나 공백 때문에 깨지지 않는가
- 브라우저가 이전 이미지를 캐시하고 있지 않은가
- 사진이 없을 때 initials 대체 기능이 작동하는가


8.5 Publications가 표시되지 않는 경우

1. publications 시트명이 유지되었는가
2. 열 이름이 변경되지 않았는가
3. 새 행이 PublicationsTable 범위 안에 있는가
4. display가 Y인가
5. 변환 스크립트가 성공했는가
6. publications.json이 갱신되었는가
7. GitHub Actions가 성공했는가
8. 로컬 서버로 접속했는가
9. Console에 fetch 오류가 있는가


8.6 특정 탭이나 필터가 작동하지 않는 경우

- Research status가 ongoing 또는 completed인가
- News type이 interview 또는 column인가
- 대문자나 한글 값을 넣지 않았는가
- app.js의 탭 기능을 AI가 삭제하거나 이름을 바꾸지 않았는가
- 관련 HTML의 ID와 class가 유지되었는가


8.7 공식 주소만 열리지 않는 경우

1. https://nam-jin.uos.ac.kr 접속 여부를 확인한다.
2. https://dockzone22.github.io/SURD-Lab/ 접속 여부를 확인한다.
3. 기본 주소는 열리는데 공식 주소만 안 열리면 DNS, CNAME 또는 HTTPS 문제일 가능성이 높다.
4. 저장소 루트에 CNAME 파일이 있는지 확인한다.
5. Settings → Pages의 Custom domain을 확인한다.
6. 학교 DNS 담당 부서에 문의한다.

학교 전산 문의 기록

- 우선 연락 내선: 6612
- 연결되지 않을 경우: 6613 또는 6611에 문의 내용을 남김

**도메인 신청은 남진 교수님 계정으로 포털 로그인>도메인 신청으로 들어가야 함. 신청 후 상신까지(가운데 쯤에 버튼이 있다)

8.8 AI 오류 진단 프롬프트

SURD Lab 홈페이지 로컬 저장소에서 [페이지]에 다음 문제가 발생했다.

11. 자주 쓰는 용어
================================================================================

- Repository: 홈페이지 파일과 변경 이력을 보관하는 저장소
- Local: 현재 컴퓨터에 내려받은 작업 사본
- Remote: GitHub에 있는 원격 저장소
- Branch: 서로 다른 작업 흐름을 구분하는 가지
- Pull: GitHub의 최신 내용을 로컬로 가져오는 작업
- Diff: 수정 전과 후의 차이
- Stage: 다음 commit에 포함할 파일을 선택하는 작업
- Commit: 변경 내용을 설명과 함께 기록하는 단위
- Push: 로컬 commit을 GitHub로 올리는 작업
- Deploy: 저장소 내용을 실제 홈페이지로 공개하는 작업
- GitHub Actions: 엑셀 변환이나 배포를 자동 실행하는 기능
- GitHub Pages: 정적 파일을 인터넷 홈페이지로 제공하는 기능
- DNS: 도메인 주소가 어느 서버로 연결되는지 알려주는 체계
- CNAME: 한 도메인을 다른 도메인으로 연결하는 DNS 기록
- HTTPS: 홈페이지 통신을 암호화하는 연결 방식
- Console: 브라우저에서 오류를 확인하는 개발자 도구 화면
- CORS: 웹페이지가 파일을 읽을 때 적용되는 브라우저 보안 규칙
- Responsive: 화면 크기에 따라 배치가 바뀌는 반응형 디자인
- Cache: 브라우저가 이전 파일을 임시 저장하는 기능


================================================================================
12. 절대 금지 행동
================================================================================

1. 원인을 모르는 상태에서 저장소 전체를 삭제하거나 새 저장소로 교체하지 않는다.
2. git reset --hard를 사용하지 않는다.
3. git push --force를 사용하지 않는다.
4. 작업 전 pull 없이 오래된 로컬 파일을 push하지 않는다.
5. 검토 없이 git add .로 모든 파일을 올리지 않는다.
6. 일상 업데이트 과정에서 전체 디자인, 헤더, 푸터와 모바일 메뉴를 재작성하지 않는다.
7. app.js의 핵심 렌더링 함수를 설명 없이 삭제하지 않는다.
8. Publications를 Excel과 data.js에 중복 입력하지 않는다.
9. publications.json을 편집 원본으로 사용하지 않는다.
10. CNAME과 GitHub Pages 설정을 콘텐츠 수정 과정에서 건드리지 않는다.
11. 비밀번호, 토큰, SSH 키, 개인정보와 비공개 원자료를 저장소에 넣지 않는다.
12. 개인정보와 비공개 원자료를 AI 대화창에 입력하지 않는다.
13. AI가 완료했다고 보고했다는 이유만으로 실제 화면 확인을 생략하지 않는다.
14. 여러 AI 또는 여러 담당자가 같은 파일을 동시에 수정하지 않는다.
15. 오류 원인을 모르는 상태에서 HTML, CSS와 JavaScript를 한꺼번에 수정하지 않는다.

삭제하거나 재정렬하지 말고 새 항목만 정확한 위치에 추가해줘. 한글과 영문 값이 서로

A.2 디자인 변경

확인해줘. 기존 색상, 글꼴, 전체 너비와 반응형 기준은 유지해줘. 고정 높이로 내용을
자르지 말고 데스크톱과 모바일에서 모두 읽히게 해줘.

공통 스타일을 건드려 다른 페이지에 부작용이 생기지 않도록 최소 범위로 수정해줘.
로컬 검증 결과와 변경 파일을 보고하고 commit과 push는 하지 말아줘.

git status와 diff를 읽고 요청 범위를 벗어난 변경, 개인정보, 비밀정보와 문법 오류를
찾아줘. data.js 배열과 객체 문법, 이미지와 링크 경로, 한영 대응을 확인해줘.

로컬 서버에서 관련 페이지와 Home을 데스크톱과 모바일 크기로 점검해줘. 문제가 있으면
수정 전에 목록으로 보고해줘. commit과 push는 하지 말아줘.


A.4 Publications 갱신

엑셀의 기존 열 이름과 표 범위를 바꾸지 말고, 새 행이 변환 대상인지 확인해줘.
scripts/convert_publications.py를 실행하여 publications.json을 갱신하고 오류를 확인해줘.

로컬 서버에서 연도 정렬, 분류 필터, DOI와 Link 버튼을 시험해줘. 원본 Excel을 보존하고
관련 없는 파일은 수정하지 말아줘. commit과 push는 하지 말아줘.


A.5 오류 진단
